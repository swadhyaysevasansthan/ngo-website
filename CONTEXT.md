# CONTEXT.md

# Swadhyay Seva Foundation --- QR Event Pass & Check-In System

## 1. Project Overview

We are adding a **QR-based event pass management and physical event
check-in system** to the existing Swadhyay Seva Foundation website and
creating a companion Android scanner application.

The system is intended for an upcoming physical event with **100+
attendees excluding chief guests and other special invitees**.

There will be **no public registration by attendees** for this pass
system. Swadhyay Seva Foundation will prepare/import the guest list in
the admin panel, generate unique passes with QR codes, distribute/print
the passes, and scan them at the event entrance.

The central business requirement is:

> A QR pass is valid only if it was generated by the Swadhyay admin
> system for the selected event, has not been cancelled, and has not
> already been checked in.

A successful scan changes:

`ISSUED → CHECKED_IN`

The same QR must never successfully check in twice.

The **backend/database is the final authority** for pass validity and
check-in status.

# 9. PHASE 2 --- Secure QR Token Generation

Every pass needs two identifiers:

### Human-readable Pass Number

Example:

``` text
SNEPC-2026-0001
SNEPC-2026-0002
SNEPC-2026-0003
```

### Secure QR Token

A cryptographically secure random token.

Do NOT use sequential IDs as security tokens.

Do NOT put the guest's name into the QR as the authorization mechanism.

The QR should encode a secure token or an appropriate secure
verification URL.

Example concept:

``` text
https://swadhyayseva.org/event-pass/verify/<secure-token>
```

The exact implementation should be chosen after inspecting the existing
website architecture.

The backend must be the authority for token validity.

After implementation:

-   Test token uniqueness
-   Test invalid tokens
-   Test cancelled tokens
-   Test expired/reissued tokens if reissue functionality is implemented
-   Update `CONTEXT.md`

# 11. PHASE 4 --- Check-In API

This is the most critical backend component.

Suggested endpoint:

``` text
POST /api/event-passes/check-in
```

Request concept:

``` json
{
  "token": "SECURE_QR_TOKEN",
  "eventId": "EVENT_ID",
  "scannerId": "SCANNER_ID",
  "gate": "MAIN_GATE"
}
```

Backend verification sequence:

1.  Authenticate scanner.
2.  Validate request.
3.  Find token.
4.  Confirm event exists and is active.
5.  Confirm pass belongs to event.
6.  Confirm pass is not cancelled.
7.  Atomically verify pass is still `ISSUED`.
8.  Change status to `CHECKED_IN`.
9.  Record timestamp.
10. Record scanner/user.
11. Record gate.
12. Create immutable CheckInLog.
13. Return result.

Success response should include:

``` text
success
result = SUCCESS
message
passNumber
guestName
category
checkedInAt
gate
```

Duplicate response:

``` text
success = false
result = ALREADY_CHECKED_IN
message
checkedInAt
gate
```

Invalid response:

``` text
success = false
result = INVALID
message
```

Cancelled response:

``` text
success = false
result = CANCELLED
message
```

Wrong event response:

``` text
success = false
result = WRONG_EVENT
message
```

The backend must never trust guest information supplied by the mobile
client.

# 24. Network Behavior

Version 1 should require internet connectivity.

Do NOT implement offline check-in initially.

Reason:

If two phones are offline, they cannot immediately know that the same
pass was already checked in on another phone.

The backend should remain the single source of truth.

If offline support is needed later, implement it as a separate phase
with explicit conflict resolution.
